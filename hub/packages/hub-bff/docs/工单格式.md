# 工单格式与看板契约 v1.1

工单为 schemaVersion 2 JSON，存于 `<root>/tickets/<id>.json`，以 `state` 表示状态。工单锁位于 `<root>/.locks/<id>.lock`；幂等索引为 `<root>/.keys/<sha256(actorName+"\0"+key)>.json`，内容为 `{id, contentHash}`。索引使用独占创建和 key 锁；工单使用临时文件及原子重命名写入。

| 字段 | 类型及含义 |
| --- | --- |
| schemaVersion、id | 固定为 2；工单 ID 格式为 `T-YYYYMMDD-HHMMSS-xxxx` |
| title、goal | 非空标题与目标 |
| key | null 或 1–128 位字母、数字、下划线、点、冒号、连字符；按发起者姓名隔离 |
| from、to | 发起者 `{name,type}`，type 为 assistant、will 或 external；to 为可领取者姓名数组，空数组允许任意有 work 权限者领取 |
| claimedBy | null 或当前领取者姓名 |
| state、review | 见下方状态与验收流程 |
| root、hop | 同一事项的根工单号，默认自身 ID；转手次数为非负整数，默认 0。多张关联工单可共用 root；创建时 hop 超限拒绝，转手加一并检查上限（默认 4） |
| expects_reply、open_ask | 是否期待回复；待人工回答时的问题 `{text,ts}`，否则为 null |
| report、reports | 最新回报及完整回报列表。每条含 `summary,file,sha256,by,ts,selfReported`，列表项还含 `artifacts` 字符串数组；summary 非空且 UTF-8 不超过 2048 字节，file 可为 null，sha256 可为 null 或 64 位小写十六进制 |
| project、sessions | 项目标识字符串；`sessions` 为 `{from,to}` 字符串 |
| workdir、forbidden、acceptance | `workdir` 为 `{path,writable}`，path 可为 null，writable 是字符串数组；forbidden 是禁止事项数组；acceptance 是 `{check,expect}` 数组 |
| progress、verification | 分别记录 `{ts,by,text}` 和 `{ts,by,verdict,note}`；verdict 为 pass、fail、partial |
| costRefs、readExternalContent | 预留的费用引用字符串数组与读取外部内容标志；不代表费用已批准 |
| routing、parentId | 预留路由 `{requestedBy,via,hint}` 字符串及父工单引用（null 或字符串）；不自动执行路由 |
| history、createdAt、updatedAt | 操作历史 `{ts,by,action,detail?}` 与 ISO 时间戳 |

同一发起者和 key 使用相同规范化内容（title、goal、to、project、workdir、forbidden、acceptance、expects_reply）时返回原工单；内容不同返回 CONFLICT。`createWithMeta` 额外返回 `deduped`，普通 `create` 只返回工单。

## 状态和验收

```text
queued --claim--> progress --report/done--> progress + submitted
                                    |             |
                                    |          accept (from) --> completed + accepted
                                    |          sendBack (from) --> progress + sent_back
                                    |                             --report--> submitted
                                    +--block--> blocked --resume--> progress
                                    +--block(waitHuman)--> waiting-human --answer/resume--> progress
                                    +--markTimeout--> waiting-timeout --resume--> progress
                                    +--markUncertain--> uncertain --resume--> progress
                                    +--fail--> failed
非终态 --handoff--> queued（更换 to、清空领取者和 review，hop 加一）
```

领取后由领取者填写进度和回报。`report` 本身将 review 设为 submitted；`done` 要求至少有一条回报，并表示交付待验收，不改变 state 为 completed。发起者可以 accept，或 sendBack 并填写修改说明；再次回报后重新进入 submitted。verification 不能由该工单已有回报的作者执行，验收不等同于验证通过。

block、fail、timeout、uncertain 和 handoff 由领取者或发起者操作，完成或失败的工单不能执行这些操作。answer 由发起者或 type 为 will 的参与者执行，清除问题并恢复 progress；resume 仅领取者可执行。接口层还需检查相应 create/work 权限。

attention 仅用于 blocked、waiting-human、failed；accept 产生非 attention 的 notify。report 和 done 事件带发起者 `inboxFor`；列表按 `inboxFor` 找该发起者 review 为 submitted 的工单，按 attention 找上述三种状态。timeout 与 uncertain 不计 attention。名册派单默认允许，明确禁用或 paused 时禁止；外部派单须明确设置 `can_dispatch_external:true`。

## 旧工单转换

旧 Markdown 工单的 queued、running、done 分别映射为 queued、progress、completed，failed 和 blocked 保持同名。creator 映射到 from，assignee 映射到 to 和适用时的 claimedBy，会话、进度与回报映射到新字段；旧回报作为自报记录，完成工单的 review 为 accepted。旧 `status`、`creator`、`assignees` 和 `needsHuman` 不出现在新格式中。无法解析或不满足新格式校验的旧内容不转换。
