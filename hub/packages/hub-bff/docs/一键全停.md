# 一键全停

## 接口（挂在 BFF 密钥校验之后，只认 `/panic/` 前缀）
- `POST /panic/stop`　可带 `{"reason":"备注"}`（≤4KB 的 JSON 对象，备注截断到 200 字）。
- `POST /panic/resume`　显式恢复；没停时是空操作（返回 `noop:true`）。
- `GET /panic/status`　当前状态，另带 `live`：此刻真在跑的会话数与外包任务数（拿不到是 `null`）。

返回里的 `state`：`running` 没停；`stopped` 所有步骤都成功（或确实不存在）；`partial` 已进入停机，但有步骤没做成。
**只有 `stopped` 才算全停。** `partial` 时 HTTP 状态是 503、`ok:false`，`steps` 里逐步写明哪一步失败、原因；
此时新的会话调用与工具调用仍然被拒（闸门和标记文件已生效），可重复调用 `/panic/stop` 重试失败的步骤。

## 各步骤（`steps` 的键）
| 步骤 | 做什么 | 怎么确认 |
|---|---|---|
| `marker` | 写停机标记文件 `<数据目录>/panic/stopped.flag`（最先做，插件靠它拒绝新的工具调用） | 写入成功 |
| `state` | 停机状态落盘 `<数据目录>/panic/state.json`（原子写，0600） | 写入成功 |
| `gate` | 在共享 `deps.sessions` 上装闸门：停机期间 `create`/`send` 一律被拒（晨会、讨论组、固定任务都走它） | 闸门已装 |
| `sessions` | 列出所有在跑的回合（含隐藏会话），逐个 `deps.sessions.cancel(id)`，轮询回查直到 0 | 回查在跑数为 0 |
| `timer:<名>` | 对配置的定时模块（默认 `meetings`、`groups`、`routines`）调 `stop()` | 只能确认 `stop()` 返回；定时器无查询接口 |
| `dispatch` | 外包运行器存在则 `stopAll()` | 再调 `listRunning()` 回查为 0 |

模块不存在记 `absent`（算成功，但如实标出）；模块存在却加载失败、缺导出、抛错、超时，一律记 `failed`。
有在跑的会话却没有 `cancel` 入口，记 `failed`，不假装停了。每一步都不因前一步失败而被跳过。

## 持久与恢复
- 状态文件或标记文件任一存在即视为已停；状态文件读不了（损坏）也按已停处理（宁停勿放）。
- 后端重启：`start(deps)` 发现仍是停机，会把所有步骤重做一遍，并在 `reapplyDelayMs` 后再补一次
  （加载器按文件名顺序启动扩展，名字排在 `panic` 之后的扩展，例如 `routines`，会晚于第一次重做才拉起定时器）。
- 恢复只能显式调用：删标记文件 → 写状态 → 对各定时模块调 `start(deps)`。被取消的回合、被停掉的外包任务**不会**自动重来。

## 配置（`hub.yaml` 的 `panic` 段，全部暂定、不是预算上限；缺省用默认）
`stepTimeoutMs` 10000　`verifyWaitMs` 3000　`verifyPollMs` 200　`reapplyDelayMs` 1000
`timers` ["meetings","groups","routines"]　`stateDir`（绝对路径，缺省 `<数据目录>/panic`）

## 接线说明（本路没改任何已有文件；以下由集成轮照做）
1. `packages/hub-bff/server.mjs`，`deps.sessions` 增加一项取消入口（没有它，有会话在跑时一键全停只会报 partial）：
   `cancel: id => client.cancel(id)`（`client.cancel` 已存在，返回 `{ok:true}`）。
2. `packages/hub-plugin/hub-config.mjs`：`PASS_SECTIONS` 加入 `'panic'`，否则 `hub.yaml` 里写 `panic` 段会被判为键错误
   （不写配置则全用默认，不受影响）。
3. **插件拒绝新工具调用**（`packages/hub-plugin/index.mjs`，`check(exec)` 里 `try{` 之后第一行）：
   ```js
   if(stopMarker(path.join(install.data_dir??path.join(install.hubHome,'hub-data'),'panic','stopped.flag')))
     return {level:'L4',reason:'已一键全停，需先恢复',path:''};
   ```
   `stopMarker(file)`：`try{fs.lstatSync(file);return true}catch(e){return e.code!=='ENOENT'}`（读不了按已停处理）。
   路径规则与 BFF 一致：`data_dir` 缺省 `<HUB_HOME>/hub-data`，再加 `panic/stopped.flag`。
4. 加载顺序：建议加载器把 `panic` 最后一个 `start`，则重启后无需靠延迟补停；否则依赖 `reapplyDelayMs` 那一次补停。
5. `packages/hub-web/server.mjs` 要转发 `/panic/`（同 `/board/` 等）；手机界面上的「全停」按钮归界面那一路。
6. 外包运行器（路 11）须导出 `listRunning()` 与 `stopAll()`；本模块只在 `lib/dispatch-runner.mjs` 存在时才调用。
7. 另一路写的新定时模块（例如 `routines`）：只要导出 `stop()`/`start(deps)` 并列入 `timers` 即被一并停与恢复；
   它们的手动「跑一次」若不经 `deps.sessions.send/create`，闸门拦不住，须自己读停机标记。

## 已知边界（如实）
- 闸门只拦经过 `deps.sessions.create/send` 的调用；主人自己从手机直接给会话发消息（`/bff/sessions/...`）不在此列，
  那是主人本人的操作，不是自动化。
- 已经通过闸门、正在飞的 `send` 会由 `sessions` 步骤的取消与回查兜住；回查到上限仍在跑则记 `failed`。
- 定时器步骤无法回查，只能确认 `stop()` 没抛错；靠闸门保证即使定时器还在响也发不出会话调用。
