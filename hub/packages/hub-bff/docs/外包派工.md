# 外包派工：把复杂的活真的交给外部命令行工人（路 11）

主人原话【Owner要求】：「只有复杂的工作才外派，他们本身也能处理一些简单的事情。」「Codex 和 Grok 到时候怎么派、
派给谁，我到时候自己跟我的 bot 们去讲，这里不用定死。」「派单之类的都要体现在看板里。」
助理不要因为一件事复杂就主动建议外派。外部派工只在主人已经点头要把整件交出去时使用。
所以：**代码只校验、不决定**——派给谁、用什么模型由工单里写（助理按主人口述的派活规则填），这里只查合不合规矩。
助理自己的命令在沙箱里跑（默认断网、连不上本机服务），所以不能靠它去起外部工人；起工人的是后端进程。

## 一张图

```
助理：dispatch_prepare 建工单（to=[工人]、routing.model、验收清单、任务书）
  → dispatch_external(工单号)               插件工具，级别 L1，只递材料：工单号、谁在派、会话读没读过外部内容
    → POST /dispatch/runs                   后端扩展，BFF 密钥之后
        第三道闸（读过外部内容？）→ 第二道闸（机器检查任务书）→ 第一道闸（放权，或出确认卡等主人）
        → 运行器起守护壳 → 壳起工人（参数数组，不经 shell）
  → 工人做完：运行器回收结果，作为「自述」写回工单，交回派单的助理验收；记一条派活账
```

## 三道闸（缺一不放行；运行器 `start()` 自己再跑一遍第二、三道，并且没有凭据就不起进程）

首席临时调用 Codex 可复用 `board_handoff` 和接单器。这个入口只需一张卡，
无需另建外包运行器或先建「等首席安排」的卡。已配置 `board.externals` 和
`board.external_launch.codex`、权限表启用 `handoff` 后，调用如下。

```json
{"to":"codex","title":"补上导出功能","goal":"在指定源码目录实现导出，完成后跑相关测试",
 "done":"交回改动文件和测试结果","return_way":"用看板交回这张工单"}
```

以上参数交给 `board_handoff`。主人在确认卡点头后，插件落下工单，现有 `ext-launch` 当场启动
配置中的 Codex 接单器。卡片内容只写进工单，启动命令仍使用固定参数数组。外部成员提问时，
`board_answer` 的回答也先出本次确认卡。内部助理间整件交接仍走 `send_to_bot`，但须主人点头且 `owner_ok` 为 true，对话里不自动转单。

1. **第一道：主人点头。** 每次外派先出确认卡，卡上显示任务书全文、工人、模型、工作目录与对象数量。
   选项是「这次派出去」「先不」。确认只作用于这一张工单和这次启动，旧的长期放权不再跳过确认。
   已有 `dispatch-grants.json` 条目仍可查看与撤销，旧卡的「以后这类不用问」答复只按本次批准处理。
   可用 `GET /dispatch/grants` 查看旧条目，用 `POST /dispatch/grants/<id>/revoke` 撤销。
   有全文存储时，任务书全文存入全文库，卡片显示最多 900 字的摘要并附「看全文」校验和。
   批准后启动前重新读取工单、重算全文校验和；内容或存储不一致就不启动、记一条错误。
   没有全文存储时，900 字以内完整出卡，超过则拒绝并要求精简或拆单。
2. **第二道：机器检查任务书。**
   - 工作目录必须在配置的外包根下**该工单自己的子目录**（`<外包根>/<工单号>/…`，工单没写目录时就用它）里，
     或在配置列出的工作树根里；解析真实路径后再比（符号链接指到外面、悬空链接、`..` 都拒）；可写路径必须在工作目录里面。
   - 任务书首行自动加上固定禁项：不投知识库、不读密钥目录、不 push、不部署、不起常驻、不删工作目录外的文件。
   - 模型必须在该工人的白名单里；工人必须是配置里的工人，且不能与助理名册重名；`to` 只能有这一位工人。
   - 验收清单至少一条（每条写清检查什么、期望什么）。
   - 任务书、标题、禁项、验收清单里出现密钥路径字样（`.secrets`、`.credentials`、`auth.json`、`.ssh`、`id_rsa`、`.aws`、
     `.netrc`、`.gnupg`、`.dsh`、作为文件名的 `.env`……）或「提权、绕过」字样（`sudo`、提权、绕过、`bypass`、`dangerously`、
     忽略之前……）直接拒；先做 NFKC 与零宽字符清洗再匹配；配置里的 `extra_deny_patterns` 也生效。
     （这会误伤「请不要去读 .secrets」这类反向写法——宁可多拒，改写成不带路径的说法。）
3. **第三道：读过外部内容不许派。** 工单标了 `readExternalContent`，或发起的会话本轮读过外部内容（认不出会话也按读过算），
   一律拒，只能转给主人看；拒绝时后端发一条通知给主人。判断只认明确的 `false`，缺了也算读过。

## 工单约定（不改看板格式，全用现有字段）

| 字段 | 用法 |
| --- | --- |
| `to` | 恰好一位，写工人名（外部身份 `{name: 工人名, type: 'external'}`） |
| `routing.model` | 模型名，须在该工人白名单里（`routing` 允许多出键，`dispatch_prepare` 同时写 `routing.worker`） |
| `goal` | 任务书正文 |
| `acceptance` | `[{check, expect}]` 至少一条 |
| `forbidden` | 本单禁项（固定禁项由代码加，不用写） |
| `workdir.path` | 空 = 外包根下以工单号命名的子目录（会自动建）；写了就按第二道闸检查 |

派单的助理（`from`）才能外派自己的单。外派后由外部身份领单、写进度、交结果；助理照常用 `board_review` 验收或退回。
被退回重做（`sent_back`）的单可以再次外派，退回意见会附在任务书最后。

## 运行器

- **不经 shell**：命令模板在配置里每种工人一条参数数组，占位符只有 `{model} {workdir} {brief_file} {result_file}`；
  任务书走文件（`stdin: 'brief'` 时喂给工人标准输入，否则工人自己读 `{brief_file}`），任务书里的引号、分号、反引号、`$()` 不会被任何东西解释。
- **脱离后端运行**：后端起一个「守护壳」（本文件 `lib/dispatch-runner.mjs` 以 `--wrap` 运行的实例），壳起真正的工人，
  落 `log`、`pid`、`child.pid`、`beat`（心跳）、`exit`（退出码）、`result.txt`（工人最后一条消息，模板里写 `{result_file}`），
  运行目录默认 `<数据目录>/dispatch-runs/<运行号>/`，另有 `brief.md`、`spec.json`、`state.json`、`manifest-before.json`。
  环境变量只放行 `env_pass`（暂定 PATH、HOME、LANG、TMPDIR），别的（含任何令牌）一律不传。
- **不自动重试、不自动杀。** 超时（`timeout_ms`，暂定 90 分钟）只把状态标成 `timeout`、工单标「超时」并出通知，进程不动；
  之后它自己结束，照常收结果（工单先恢复再交结果，`timedOut` 保持为真）。
- **同一工作目录同一时刻只许一张在跑**（目录锁在 `.workdir-locks/`），第二张得 `BUSY`；同一张工单重复外派得到「已在跑」，不起第二个进程。
- **回收**：后端启动时 `recover()` 读运行目录，认回还在跑的（凭 `pid` 与心跳，进程没了又没留退出码就标 `lost`、工单标 `uncertain`）；
  有人查看（`GET /dispatch/runs[/<id>]`、再次调用 `dispatch_external`）和定时（`poll_ms`，暂定 3 秒，0 为关）都会回收。
- **结果写回工单**：成功时一条自述报告（`selfReported`），摘要以「【外部工人自述，未验证】」开头，含工人、模型、退出码、用时、运行号、
  最后一条消息；`artifacts` 是开工前后对比出的改动文件清单（新增、修改、删除，超过 `max_changed_files` 只列前 N 并写总数）。
  退出码非 0、被停掉、没能启动：工单标 `failed` 并写原因。**这些都是工人的自述，要助理或主人验收，不算已验证。**
- **派活账**：每次运行收尾记一行 `kind: 'dispatch'`（`worker`、`workerModel`、`wallMs`、`exitCode`、`outcome`）；
  token 拿不到，写 `null`（不写 0）。
- **一键全停**：`ext/dispatch.mjs` 导出 `listRunning()` 与 `stopAll({kill})`，给「一键全停」那路按 `ext.module('dispatch')` 调用。
  `stopAll` 向进程组发 SIGTERM，等 `stop_wait_ms` 后**如实**返回 `{stopped, stillRunning, errors}`；不自动 SIGKILL，
  除非 `stopAll({kill:true})`。停掉的运行，工单标 `failed`，原因写「被一键全停停掉」。

## 安全边界（别把三道闸当成沙箱）

- 工人是以后端进程同一个用户身份跑的命令行程序，环境变量虽然只放行 `env_pass`，但它仍能读到该用户能读的文件。
  真正的隔离靠工人自己的沙箱（例如命令模板里写工人自带的「只许写工作目录」选项），三道闸是在它起来**之前**拦住不该派的活。
  任务书里的固定禁项是写给工人看的，不是机器执法。
- `/dispatch/*` 只挂在 BFF 密钥之后（扩展加载器的私有阶段）。**不要**把它加进网页层转给手机的路径，
  也不要给外部看板令牌开放；看板远程入口只认 `/board/*`。
- 工人的自述会进工单摘要；任何页面把它画出来时都要当纯文本（路 18 复核点）。

## 配置（`hub.yaml` 的 `dispatch` 段，或配置目录下的 `dispatch.json`）；没配置就是没开通（接口回 503）

```json
{
  "root": "<外包根目录，绝对路径>",
  "worktree_roots": ["<允许直接在里面干活的工作树根，可空>"],
  "allow_bots": ["<可外派的助理 id，或 *>"],
  "workers": {
    "<工人名>": {
      "argv": ["<可执行文件>", "exec", "-m", "{model}", "--output-last-message", "{result_file}", "-"],
      "models": ["<允许的模型名>"],
      "stdin": "brief"
    }
  },
  "timeout_ms": 5400000, "grant_days": 14, "card_text_max": 1000, "card_ttl_ms": 21600000, "poll_ms": 3000
}
```

数字全部**暂定**，没有任何费用上限（预算上限晚点再说【Owner要求】）。命令模板是安装者写的，不由模型也不由工单决定。
未写 `allow_bots` 时，名册里所有启用的助理均可发起；`[]` 禁止全部，`"*"` 或 `["*"]` 允许全部启用的助理，
名单只允许列出的助理。停用或暂停的助理始终不能发起。默认每次都要确认，只有主人为该类任务放权后才免问。
插件那一侧要连后端，读同一个 `dispatch` 段里的 `bff_url`、`bff_key_file`（没有就用 `groups` 段的同名键），只许本机回环地址。

## 接线说明（本路只新建文件；以下是集成轮要改的地方）

1. 扩展：`lib/ext/dispatch.mjs` 放进 `lib/ext/` 就会被加载器挂到 `/dispatch/*`（私有阶段，要 BFF 密钥）。无需改 `server.mjs`。
2. 配置：`packages/hub-plugin/hub-config.mjs` 的 `PASS_SECTIONS` 加上 `'dispatch'`（否则安装配置里写 `dispatch` 段会被判为未知键；
   不改也行，后端回退读 `dispatch.json`，但插件那侧读不到 `allow_bots`，就要靠名册行或 `groups.bff_url`）。
3. 权限表：`plugin_tools` 名单加 `dispatch`（工具模块 `tools/dispatch.mjs` 才会注册），两个工具级别都是 L1：
   确认卡由后端出，因为内核那张卡的预览只有 200 字，装不下任务书全文。
4. 确认卡接口：`runtime.ask` 接收全文校验和；长任务书用全文库与卡片摘要，不受卡片正文 1000 字上限影响。
5. 一键全停：路 12 的 `panic.mjs` 调 `ext.module('dispatch')?.stopAll()` 与 `listRunning()`；通知里 `source: 'dispatch'` 的事件界面可选择性展示。
6. 看板显示：外派后工单的 `claimedBy` 是工人名、`claimedByType` 是 `external`，进度里有「已外派…运行号…」；界面需要能显示 external 的领单人。
7. 主人没批准或卡超时：只发通知，工单仍是待领取（看板没有「发起人追加备注」的接口，所以不能写进工单），需要时助理再调一次。

## 没做、没验

- 没起过真的 Codex 或 Grok；模板里的参数（例如 `--output-last-message`）要上线时对着真命令核一遍。
- 后端在主人答卡之前重启，这张卡的后续处理就丢了（卡还在，但没人等它）；助理再调一次 `dispatch_external` 会重新出卡。
- 文件清单靠开工前后的指纹对比，条目超过 `max_scan_entries`（暂定 5000）时标「可能不全」。
